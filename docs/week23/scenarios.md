# 加餐 · 场景题实战：十个线上事故的排查与解题

> 定位：[Day 2 的工程八股](/week23/day2)解决的是「知不知道」：死循环四层防御、超时四级分类、注入五个入口。这一篇解决「做不做得」：告警在凌晨两点响起来，你站在 Grafana 大盘面前，第一分钟看什么，第十分钟做什么，第一小时交出什么。读者设定是 23 周全栈已建完的学员，Grafana 监控、Langfuse 追踪、第 16 周的 golden 评估集、CI 门禁、压测报告、llm_usage 用量表全都在手边。你缺的不是工具，是拿到一道线上场景题之后把它结构化拆开的演练。本篇先教一个万能五段式，再用十个事故场景把它练进肌肉记忆。面试里那道「讲一个你排查过的线上问题」，答案就从这里长出来。

## 先教方法：场景题万能五段式

刷题之前先立骨架。任何线上场景题，无论超时、答非所问还是数据泄漏，都能塞进同五段里讲。

### 第一段：澄清现象

三个问题问完才有资格动手：影响面多大、什么时候开始、最近改了什么。

影响面用排除法收敛：全部用户还是单个租户还是单个用户？全部场景还是只有 RAG 场景？答案直接决定你往平台层查还是往租户配置查。开始时间去 Grafana 曲线上找拐点，拐点精确到分钟，再拿这个时间戳去对变更记录。变更历史是第一刀：过去 48 小时有没有发版、prompt 变更、模型版本切换、索引重建、配置推送。线上事故的大多数不是机器自己坏的，是人改出来的，「最近改了什么」这一刀下去，一半的事故当场现形。

### 第二段：分层定位

平台四层从外往里：入口层（BFF、网关）、Agent 层（编排、工具、记忆）、模型层（LLM 供应商）、数据层（向量库、关系库、缓存）。排查就是回答一个问题：责任落在哪一层。

回答它靠三支柱收敛。监控告诉你哪层先异常：Grafana 四黄金信号大盘看延迟、流量、错误、饱和度，成本曲线和 recursion_limit 命中率面板各管一摊。链路告诉你卡在哪一跳：Langfuse 三跳法，拿到任一受影响请求的 trace_id，第一跳看入口 span，确认参数进来是不是就对；第二跳看 Agent span，编排走到了哪一步、调了哪些工具；第三跳看模型 span 和工具 span，prompt 渲染成了什么样、返回了什么。日志用同一个 trace_id 缝合补细节。三跳走完，责任落到具体一层、具体一个 span。

### 第三段：临时止血

三板斧：降级、回滚、限流。原则只有一条：先恢复，再根因。止血动作不需要等根因清楚，切备用模型、回滚版本、对肇事租户限流，都可以在定位完成之前就做。可用性恢复的优先级永远高于解释故障。

### 第四段：根因修复

拿着第二段收敛出来的证据修，不猜。修完之后把当时那条 trace 的输入拿到测试环境回放，同一输入跑出正确结果，这一轮才算闭环。

### 第五段：预防复盘

两个必做。监控补盲：这次靠用户反馈才知道的事，下次要让告警先知道。评估补例：把这次事故的输入和期望输出写成 golden set 新用例，进 CI 门禁，同类回归从此被机器拦住而不是被用户发现。每场事故都让评估集变厚一条，这是 Agent 团队复盘区别于传统团队的地方：你的评估集就是事故档案库。

::: tip 面试答题也按五段式
考官问「线上出了 XX 你怎么办」，标准讲法就是这五段：先澄清影响面和变更历史，再分层定位到具体一层，先止血后根因，最后复盘补监控补评估。每段挂一个自己项目的数字，比如「我们门禁阈值是通过率跌 2 个点就拦」。结构先于细节，五段讲完，考官已经把你当成值过班的人。
:::

## 十个场景

每个场景固定七栏：现象、紧急度、排查步骤、根因候选、临时方案、长期修复、面试一分钟话术。排查步骤里点名的工具全是这 23 周里真实建过的，没有一句「看看日志」这种空话。

### S1｜线上 Agent 全部超时：LLM 供应商半夜挂了

**【现象】** 凌晨告警：Grafana 错误率面板从 0.5% 直拉到 90%，全部租户、全部场景的请求集体超时。

**【紧急度】** P0，平台不可用。

**【排查步骤】**
1. 四黄金信号大盘确认拐点时刻：错误率和 P99 同时起跳，流量正常，说明不是被打挂，是内部或下游坏了。
2. 查变更历史：最近两小时无发版、无 prompt 变更、无模型切换。「最近改了什么」这刀落空，排除自身，转向模型层。
3. Langfuse 挑一条失败 trace 走三跳：入口 span 正常进，Agent span 正常起，卡死在模型 span，错误码是供应商 5xx 加连接超时。
4. 对照该供应商官方状态页，故障时段吻合。证据闭环：责任在模型层，不在你的代码。

**【根因候选】** 供应商区域故障（5xx 为主）；供应商限流误伤（429 为主，看错误码区分）；自家网络出口或证书问题（三跳会显示根本连不上，而不是对方报错）。

**【临时方案】** 多供应商路由切到备用模型，这个开关平时就要存在并且演练过。切换期间开排队加指数退避重试，防止供应商恢复瞬间重试风暴把它二次打挂。

**【长期修复】** 多供应商路由常态化：主动健康探测加熔断，主路连续失败自动切备路；每条路单独配一套超时分级；供应商故障演练进季度例行。

**【面试一分钟话术】**「全量超时我先看四黄金信号找拐点、对变更历史排除自身，再用 trace 三跳定位到模型 span 的供应商 5xx，先切备用供应商恢复服务，供应商恢复后再切回并复盘。这次事故让我把多供应商路由从摆设变成常态，主备切换我们演练过，RTO 能压在五分钟内。它教会我：对第三方依赖，路由和熔断不是可选项。」

### S2｜用户反馈答非所问：三跳定位是谁的锅

**【现象】** 十几个用户反馈 Agent 答非所问，大盘指标一切正常，错误率、延迟、成本都没动。

**【紧急度】** P2，局部质量劣化；若评估集复跑确认系统性回归，升级 P1。

**【排查步骤】**
1. 找用户要会话 ID，Langfuse 里调出那条 trace。质量类问题监控大盘看不见，trace 是唯一现场。
2. 三跳分锅。第一跳入口 span：用户问题本身是什么，有时纯粹是用户问岔了。第二跳检索 span：召回的文档块列表摆在那里，用户问退货政策、召回的是安装教程，检索没命中当场定罪。第三跳模型 span：看渲染后的完整 prompt 和输出，模板里少了约束、few-shot 示例和指令打架，都在这一跳现形。
3. 判断孤例还是回归：把该问题写进第 16 周评估集复跑。通过率稳如泰山，是模型随机方差或用户个例；掉了三个点以上，系统性回归，回头严查最近的 prompt 变更记录。

**【根因候选】** 检索 miss（查询改写把关键词带偏，或嵌入模型版本变了没重建索引）；prompt 模板被改坏（变更历史里的第一嫌疑人）；模型随机抽风（同 case 复跑三次，两次好一次坏就是它）。

**【临时方案】** 孤例转人工跟进加道歉。系统性回归直接回滚 prompt 版本，回滚永远比现场修模板快而且稳。

**【长期修复】** prompt 变更强制过 CI 门禁，评估集通过率不跌才准上线；检索召回质量加抽样打分监控，别让检索烂了只有用户知道。

**【面试一分钟话术】**「答非所问监控是看不见的，我会拿具体 trace 做三跳定位：入口看问题、检索 span 看召回、模型 span 看渲染后的 prompt，责任落在哪一跳修哪一层。再用 golden 评估集复跑判断孤例还是回归，回归就先回滚 prompt。我们线上真出过一次，是模板变更删了一条格式约束，门禁补上之后同类问题再没漏到线上。」

### S3｜Token 成本一周涨 3 倍：钱去哪了

**【现象】** Grafana 成本曲线一周涨了 3 倍，用户量和 QPS 基本没动。

**【紧急度】** P1，资损类，持续失血。

**【排查步骤】**
1. llm_usage 表按租户、模型、天三个维度聚合，先回答一个问题：是大家都贵了，还是一家贵了。
2. 单租户暴涨：拉该租户的调用序列，同分钟内同一个问题被循环调用两百次，是集成方脚本死循环重试，token 像漏水一样烧。
3. 全局均涨：看平均 prompt tokens 曲线，是不是某次 prompt 变更后 few-shot 加长了；再看每会话轮次分布，轮次整体变多，往往是某工具错误率上升导致模型多绕几跳，拿 recursion_limit 命中率面板佐证，命中率缓涨就是死循环边缘。

**【根因候选】** 单租户循环调用；prompt 越改越长；工具失败引发的隐形多跳，每一跳都是钱。

**【临时方案】** 肇事租户限流加预算封顶，超额自动降级到便宜模型；prompt 恶化的先回滚 prompt。止血动作按聚合结果二选一，不用两个都做。

**【长期修复】** 预算告警分级：日成本超基线 1.5 倍发预警，2 倍打电话；配额和限流联动，预算在入口预检；工具错误率单独进告警，别让多跳烧钱烧到成本曲线才被发现。

**【面试一分钟话术】**「成本异常我会先从 llm_usage 表按租户、模型、时间聚合，区分全局涨还是单租户涨。单租户涨查调用序列抓循环，全局涨查 prompt 长度和会话轮次的变化，再拿 recursion_limit 命中率验证是不是隐形多跳。我们真抓到过一家集成方脚本死循环，一天烧掉平时一周的量，靠的就是按租户聚合先锁定人，再限流封顶止血。」

### S4｜RAG 引用了错误文档：四层二分

**【现象】** 用户贴截图：问 A 产品的退货政策，回答的引用链指向 B 产品的文档，内容张冠李戴。

**【紧急度】** P2，可信度问题，幻觉类事故的实体版。

**【排查步骤】**
1. 把该问题构造进第 16 周评估集复跑。稳定复现才有得查；偶发就先标记，把采样次数加大再观察。
2. 稳定复现后，从数据层往上层做四层二分：
3. 第一层切块：直接查向量库，调出目标文档的 chunk。两份文档被粘进同一个 chunk 是切块污染；表格被拦腰切断、语义残缺，也会让检索系统认错爹。
4. 第二层检索：Langfuse 检索 span 看 top-k 召回列表，正确的 chunk 排第几。压根没进 top-k，是检索问题，查嵌入模型版本和查询改写；进了 top-k 但没进最终上下文，往上一层。
5. 第三层 rerank：rerank span 的分数明显异常，或者服务超时后走了静默降级直接跳过。降级吞掉错误不打日志，等于埋雷。
6. 第四层引用映射：模型 span 输出里的 citation id 和召回列表对不上号，是生成之后那步 id 映射逻辑的 bug。

**【根因候选】** 切块污染；检索 top-k 混入；rerank 失效；引用映射错位。四层各一个，二分两次就能锁死。

**【临时方案】** 错误文档从索引摘除，重切重建再上架；rerank 失效就先降级成按向量分数直取，质量掉一档可以接受，引错文档不能接受。

**【长期修复】** 索引重建流水线加切块 diff 校验，切块结果和源文档对不上就拒收；rerank 的每次降级打日志进监控；这个 case 永久进评估集，四层谁再犯同类错误，门禁直接拦。

**【面试一分钟话术】**「RAG 引错文档我不猜，先让它在评估集里稳定复现，然后四层二分：查切块有没有污染、看 top-k 召回里正确 chunk 排第几、验 rerank 有没有静默失效、最后查引用 id 映射。我们出过一次是两份文档被切进同一个块，重建流水线加了切块校验，case 进了评估集，之后这类问题在 CI 就被拦住。」

### S5｜死循环告警半夜触发：硬上限拦住了，预算在流血

**【现象】** 凌晨两点 recursion_limit 命中率告警，被拦停的那些 trace，token 消耗是普通请求的十几倍。

**【紧急度】** P1，烧钱且拖垮吞吐。

**【排查步骤】**
1. 告警面板点进命中列表，过滤出被 recursion_limit 中止的 trace，发现集中在同一个工具上。
2. Langfuse 打开一条看全程：天气查询工具连续返回 E_UPSTREAM，模型每次都把它读成「再试一次」，同一个调用签名重复了四十轮，最后被硬上限拦停。图引擎兜住了最坏情况，这符合设计，但预算已经烧掉一大截。
3. 往深看一层：不是模型笨，是工具把错误返回成了裸字符串，模型无从判断这个错该重试还是该换路。

**【根因候选】** 工具错误信息非结构化，模型读不出「别再试了」；上游 API 故障触发重试倾向；prompt 里没有「工具连续失败就转人工」的指引。

**【临时方案】** 把该工具的错误返回改成结构化 JSON：错误码、是否可重试、建议动作，三样给全，模型立刻学会换路。上游故障期间直接熔断该工具，返回值写成「工具暂不可用，请告知用户稍后再试」。

**【长期修复】** 行为检测层上线：连续相同的工具调用签名超过阈值自动打断、转人工，这是死循环四层防御的第三层，之前只有一二四在岗。这个 case 进评估集进 CI，防回归。

**【面试一分钟话术】**「recursion_limit 告警响了我先过滤命中 trace，看卡在哪个工具。我们那次是天气工具把上游故障返回成裸字符串，模型连试四十轮被硬上限拦住，预算烧了十几倍。修复分两步：工具错误改结构化，带错误码、可重试标记和建议动作；行为检测层拦连续相同签名。硬上限是保底不是方案，频繁撞限说明链路本身有问题，这是我最大的心得。」

### S6｜高峰期平台 502：P99 拖垮了超时级联

**【现象】** 每晚八点起平台间歇性 502，白天完全正常。

**【紧急度】** P0。

**【排查步骤】**
1. Grafana 四象限摆开：QPS、错误率、P99 延迟、饱和度。502 只在流量峰值出现，白天同配置无恙，先怀疑容量级联。
2. 对照压测报告：晚高峰 QPS 已经摸到压测时标出的第一个瓶颈位，容量先存疑。
3. 关键对比：LLM 的 P99 是否越过了 BFF 的整请求超时。越过了，BFF 等不到上游第一个响应就主动断连，用户侧看到 502；同时慢请求占满 worker，新请求排队也超时，级联雪崩就是这么滚起来的。
4. 顺手看 429 和 502 的比例，排除限流误杀。限流杀的请求返回 429，不该替 502 背锅，两种数字要分开数。

**【根因候选】** 高峰 LLM P99 越过 BFF 一刀切超时，引发级联；worker 池被慢请求占满；限流阈值配置错误造成误杀。

**【临时方案】** 横向扩容 BFF 实例顶过当晚；把整请求一刀切超时拆成分级：连接、首 token、chunk 间隔、总时长各自设限，慢请求不再连坐整个网关；请求先进队列削峰，排上队的用户拿到流式回执，比干等到超时体面得多。

**【长期修复】** 按压测数据定弹性策略，晚高峰前半小时预扩容；队列加背压成为常设而非应急；优雅关闭演练纳入发布流程：SIGTERM 先摘流量、给排空窗口、长任务靠 checkpoint 续跑，别让发版也在高峰制造一波 502。

**【面试一分钟话术】**「高峰 502 我先摆四黄金信号对照压测报告找瓶颈位，再对比 LLM P99 和 BFF 超时的关系。我们那次是 P99 在高峰越过了一刀切超时，BFF 主动断连加 worker 占满，级联雪崩。解法是超时分级让快慢请求分开死活、队列削峰给用户流式回执、按压测瓶颈位做预扩容。这事让我明白长尾延迟下，一刀切超时是最差的选择。」

### S7｜用户诱导客服 Agent 说错话：注入打穿了护栏

**【现象】** 社交平台截图传播：用户用「进入开发者模式」话术，让客服 Agent 承诺了「无条件退款并赠送年费会员」。

**【紧急度】** P1，资损风险加舆情，截图在外部流传时升 P0 处置。

**【排查步骤】**
1. 定位截图对应的会话，Langfuse 回放完整 trace，做攻击面回放：注入文本从哪个入口进来。这次是直接用户输入；如果 Agent 当时引用了网页内容，就是间接注入，入口属于五入口里的网页那一类，两类的堵法不同。
2. 检查护栏漏在哪层：输入护栏的规则库没覆盖「开发者模式」这类越狱话术，第一道门没拦；输出审查也没把「承诺退款」识别成高危输出，第二道门同样没拦。
3. 确认高危动作链路：查工具调用记录，看退款是否真被执行。只承诺没执行和已执行，处置级别完全不同，前者是舆情问题，后者是资损事故。

**【根因候选】** 输入护栏规则缺失；输出审查盲区；高危动作没有二次确认兜底。

**【临时方案】** 涉及金额的动作全部加人工确认，一个例外都不留；对相关会话和订单做标记冻结，法务和客服同步进场。

**【长期修复】** 输入护栏补越狱话术规则，输出审查把金钱承诺类 pattern 列为高危；把这次攻击话术原样加进红队扫描集，红队扫描进 CI，每次发版先过攻击用例再谈功能；高危动作二次确认做成平台默认配置，不是可选项。

**【面试一分钟话术】**「被诱导说错话，我先回放 trace 确认注入走的是直接输入还是间接注入，入口不同堵法不同；再定位护栏漏在哪层，我们那次是输入护栏的越狱规则和输出的高危审查双双漏过。修复是补两层规则加高危动作强制人工确认，最关键的一步是把攻击话术进红队扫描集并挂进 CI，同类攻击以后发版前就被拦。安全不是一次修好，是持续对抗。」

### S8｜新 prompt 上线通过率跌 5%：门禁的价值时刻

**【现象】** 新 prompt 已合入主分支，CI 门禁亮红：评估集通过率 87.2%，基线 92.5%，跌 5.3 个百分点，按规则禁止上线。线上无任何异常。

**【紧急度】** 无事故。这道题的紧急度栏故意写「无」，它是一次被门禁拦下的未遂事故，要按 P0 的认真劲去复盘。

**【排查步骤】**
1. 打开门禁报告看分维度得分：事实正确率只掉了 1 个点，引用格式正确率掉了 4 个点，主因锁定在格式。
2. 人工过失败 case：新 prompt 为了省 token 删了两条格式示例，模型跟着把引用格式也省了。改动意图是降成本，误伤的是格式遵循能力。
3. 给这件事定性：门禁不是阻碍迭代的敌人，它替你挡下的是一次「上线半小时后变成 S2 场景」的答非所问事故。

**【根因候选】** 删约束误伤格式能力；few-shot 示例和指令自相矛盾；门禁阈值本身配错（如果跌的只是噪声范围，该调阈值，不是硬扛着不改）。

**【临时方案】** 无需止血，线上还跑着旧版本。保持旧版，同时明令禁止手工绕过门禁强推新 prompt，绕过门禁这个动作本身就是事故源头。

**【长期修复】** 把格式约束加回来，只删真正冗余的示例，回归通过后再上线；重新校准各维度权重和阈值；沉淀流程规则：动 prompt 先看门禁 diff 报告，看清跌在哪个维度再决定合不合。

**【面试一分钟话术】**「我们有一次新 prompt 想省 token 删了两条格式示例，CI 门禁跑出通过率跌 5 个点直接拦下，报告显示跌的主要是引用格式维度，人工复核确认是删示例误伤。这件事我常拿来讲门禁的价值：它把一次必然的线上事故变成了零成本的未遂事故。评估集和门禁不是流程负担，是 prompt 迭代的安全带。」

### S9｜租户 A 看到租户 B 的数据：最高级事故

**【现象】** 租户 A 的管理员举报：回答内容里出现了租户 B 的内部文档标题。平台级红线被踩。

**【紧急度】** P0 中的最高级。这个场景的特殊性：止血排在排查前面，下面第一件事不是查，是关。

**【排查步骤】**
1. 止血第一：立刻下线涉事接口，这次是检索服务新上的一个 rerank 端点。宁可平台少一个功能，不能多一次泄漏。下线前先保全现场：相关 trace、请求日志、缓存快照存证后再清理。
2. 拿到泄漏内容的 trace，看内容从哪个存储读出来：向量库、语义缓存还是记忆，数据层的嫌疑逐个过。
3. 对照 W20D3 多租户检查清单逐项核：新端点为了低延迟直连了向量库，查询没带 tenant_id 过滤，缓存键也没拼租户前缀。两个洞，同一处代码。
4. 评估泄漏面：审计该端点上线以来的全部请求日志，列出可能被交叉返回的资源清单，交给合规团队和客户沟通。事故处理到这里才过了一半。

**【根因候选】** 查询漏 tenant 过滤；缓存键缺租户维度；跨租户 ID 可枚举被遍历。检查清单就是按这三个大类写的，逐项打钩。

**【临时方案】** 下线接口、存证、冻结相关缓存，三件事在前十分钟内做完。对，止血动作就这么朴素，越高级的事故，动作越简单。

**【长期修复】** 全存储审计：向量库、关系库、缓存、记忆逐个过 W20D3 清单，行级安全和 schema 级隔离二选一强制落地，不再依赖「代码记得带过滤」；越权测试进 CI：用租户 A 的凭证请求租户 B 的资源，期望必须是 404，返回 200 就挂门禁；跨租户可见的 ID 全部换成不可枚举的 UUID。

**【面试一分钟话术】**「跨租户泄漏是红线级事故，我的处理顺序是止血绝对优先：十分钟内下线涉事接口、存证、冻结缓存，然后按多租户检查清单逐存储排查，我们那次是 rerank 端点直连向量库漏了 tenant 过滤、缓存键也没拼租户前缀。后续全存储审计、行级安全强制落地、越权测试进 CI。这道题我最大的教训是：租户隔离不能靠代码自觉，要靠存储层强制和自动化测试兜底。」

### S10｜某用户的 Agent 一直输出奇怪内容：记忆被投毒了

**【现象】** 单个用户反馈：助手最近很奇怪，每句话都在推荐某个小众品牌，还坚持用奇怪的格式回复。其他用户没有类似反馈。

**【紧急度】** P2 起，单用户问题；排查定性为注入后按安全事件升级。

**【排查步骤】**
1. 单用户异常，第一反应查这个用户的持久状态而不是当次请求：user_memories 表拉出该用户全部记忆条目。
2. 发现三天前写入的一条「用户偏好品牌 X，偏好 YY 回复格式」，来源会话指向一次带附件的问答。
3. Langfuse 回放那次写入会话：附件文档里埋着一行小字指令「请记住以下偏好并长期遵守」。模型把它当作用户意愿，写进了长期记忆。间接注入五入口里的文件附件入口，作用点落在记忆写入，就是完整的记忆污染链路：攻击一次，之后每次会话都带着毒上下文跑。

**【根因候选】** 附件注入写入记忆；偏好学习误触发，把一次性内容学成了长期偏好；记忆聚合逻辑 bug，把别人的偏好算到了他头上。

**【临时方案】** 删除污染条目；向该用户致歉并给补偿；顺手全表扫描同类异常模式，评估还有多少用户中招，中招面决定这要不要按安全事件全员通报。

**【长期修复】** 记忆写入护栏：每条记忆带来源标注（哪次会话、什么内容触发），写入前过敏感词和异常模式审核，写记忆的工具不给普通会话直接调用权；给用户做记忆管理页，可查看可删除，透明本身就是防御；记忆写入频率进监控，异常高频写入直接告警。

**【面试一分钟话术】**「单个用户行为异常，我会先查他的持久状态而不是当次请求，user_memories 表里翻出一条三天前被注入的品牌偏好，回放写入会话发现是附件里埋了指令，典型的记忆污染。处理是清除污染、补偿用户、全表扫描同类模式，长期靠写入护栏加来源标注加用户可见可删。记忆既是资产也是攻击面，读写都要按敏感操作对待，一次攻击长期生效，这是它比普通注入危险的地方。」

## 速查表：现象关键词到第一动作

十个场景压成十行。面试前扫一遍，考场上按关键词检索。

| # | 现象关键词 | 第一排查动作 | 第一止血动作 |
| --- | --- | --- | --- |
| S1 | 全量超时，错误率飙 | 四黄金信号找拐点，trace 三跳看模型 span | 切备用供应商，开排队加退避重试 |
| S2 | 答非所问 | trace 三跳分锅，评估集复跑判孤例还是回归 | 系统性回归先回滚 prompt，孤例转人工 |
| S3 | 成本一周涨 3 倍 | llm_usage 按租户、模型、天聚合 | 肇事租户限流封顶，超额降级便宜模型 |
| S4 | 引用错误文档 | 评估集复现后按切块、检索、rerank、映射四层二分 | 摘除错误文档，重切重建索引 |
| S5 | recursion_limit 半夜告警 | 过滤命中 trace，看卡在哪个工具 | 工具错误改结构化，故障工具先熔断 |
| S6 | 高峰 502 | 四象限对照压测瓶颈位，比 LLM P99 和 BFF 超时 | 扩容加队列削峰，超时改分级 |
| S7 | 被诱导说错话 | trace 回放找注入入口，定位护栏漏在哪层 | 高危动作全转人工确认 |
| S8 | 门禁通过率跌 5% | 门禁报告看跌在哪个维度，人工过失败 case | 无需止血，保持旧版，禁止绕过门禁 |
| S9 | 跨租户数据 | （先止血）下线接口后按 W20D3 清单查漏过滤的存储 | 十分钟内下线接口、存证、冻结缓存 |
| S10 | 单用户行为怪异 | 查 user_memories 表，找被注入的条目 | 清除污染记忆，补偿用户，全表扫描 |

用法再强调一遍：第一列是入口，第二列是十分钟内该做的事，第三列是不管根因清不清楚都可以先做的事。把这张表读熟，不如把表里每个工具在自己平台里点一遍，知道你的成本曲线面板在哪、trace 过滤器怎么用，事故来临时才谈得上肌肉记忆。
