# 读代码前先读这篇：Agent 的护栏防什么，怎么防

> 本目录解决 Agent 的"手"不可信问题。模型**会被骗**（注入话术顺着工具参数溜进来）、
> **会泄密**（工具输出里夹带真实手机号/身份证/银行卡号）、**会自作主张**（高危工具
> 说调就调）。护栏的本质：**在工具执行边界上加检查点，而不是信任模型**——输入闸拦
> 脏参数、输出闸拦敏感数据、闸门拦高危执行。与 `evals/`、`memory/` 同一套工程哲学：
> 纯函数优先、零依赖零网络零 key（`pnpm test` 里护栏套件必跑、不设任何门控）。
> 配合教程 [week18 · Day 5：MCP 安全护栏](../../../../../docs/archive/weeks/week18/day5.md)
> （输入输出校验 + PII 脱敏）；**人工审批是 [Day 6](../../../../../docs/archive/weeks/week18/day6.md)，
> 落在 `apps/api/src/chat/tool-approval.ts`**——同一抽象的姊妹实现，见第七节交叉引用。

---

## 一、第一性原理：能力越大，越不能裸奔

Agent 接上工具（尤其 MCP 外部服务器）之后，身份从"一张嘴"变成"有手有脚"——
教程 Day 5 说麻烦从三个方向来，正好对应三类风险：

1. **会被骗（Prompt Injection）**：用户输入或工具参数里藏一句"忽略之前的所有指令"，
   模型未必分得清这是业务诉求还是攻击载荷——它太听话了；
2. **会泄密（PII 外流）**：外部工具的输出要回灌给模型、也可能转述给用户——一旦里面
   夹带真实号码，泄露面就从"服务器日志"扩大到"模型上下文 + 会话存储 + 对话记录"；
3. **会自作主张（高危无闸）**：写操作类工具（建工单、退款）直接执行，模型觉得该调
   就调，没有人这一道闸。

为什么检查点加在**工具边界**而不是模型边界？prompt 无论怎么打磨，模型终究是
概率性的；而 `execute` 前面的检查是代码，**确定性的**——确定性防线放在确定性
边界上，与 `evals/` Tier 1 先做确定性断言同一哲学。但也要诚实（`validate.ts`
头注释原话）：这是**纵深防御的一层，不是银弹**——字符串匹配只拦"明示型"注入，
语义级改写超出它的能力范围。

## 二、核心设计：两道闸 + 一个门

| 零件 | 文件 | 职责 |
| --- | --- | --- |
| 输出闸 | `pii-mask.ts` | 中文语境 PII 打码：手机号 / 身份证 / 银行卡（边界锁死，长串不误拆） |
| 输入闸 | `validate.ts` | 规范化 + 注入黑名单扫描；白名单解析与判定 |
| 门 | `gate.ts` | `wrapToolWithGate`：把「白名单 → 输入闸 → 确认 → 原执行 → 输出闸」套在任意工具外 |
| 出口 | `index.ts` | 桶导出（刻意不加 package.json 子路径，统一从包根出口走） |

门内五步的执行顺序是**成本排序**：白名单（O(1) 集合判定，最便宜）→ 注入扫描
（纯函数正则）→ 人工确认（可能要终端交互，最贵且只有静态闸都放行才值得问人）→
原 `execute` → 输出脱敏。前置闸任一命中直接短路返回拒绝，**绝不触碰原 execute**：

```text
调用方/循环 ──► ① 白名单闸（不在名单 → 拒绝）
              ├─► ② 输入闸（入参 JSON 序列化 → 规范化 → 注入黑名单）
              ├─► ③ 确认闸（confirm 回调，false/抛错都算拒绝）
              ├─► ④ 原 execute（正常结果与异常都原样上抛——闸门不吞）
              └─► ⑤ 输出闸（maskOutput 开：序列化 → maskPii → 解析回结构）
                                    任何一步被拦 ──► { denied: true, reason }（不是异常）
```

装配在 `apps/cli/src/apps/chat/cli.ts`：`AGENT_GUARD_*` 三开关、只给 MCP 来源的
工具套闸、全关零变化——接线细节见 3.4。

## 三、各部分原理

### 3.1 输出闸：PII 脱敏（pii-mask.ts）

三条正则，全部**环视边界锁死**——候选的前面或后面紧邻数字就放弃匹配：

```text
手机号  (?<!\d)1[3-9]\d{9}(?!\d)          11 位，1 开头第二位 3-9
身份证  (?<!\d)\d{17}[\dXx](?![\dXx])     18 位，末位可 X/x
银行卡  (?<!\d)\d{13,19}(?!\d)            13~19 位连续数字
```

**为什么边界纪律是第一位的**（`pii-mask.ts` 头注释列了两种事故）：没有 `(?<!\d)…(?!\d)`，
① 20 位数字串会被当成"19 位银行卡"的前 19 位截出来打码（错拆）；② 身份证（18 位）
内部的 11 位窗口会被当成手机号二次打码（错拆 + 二次泄露形态）。测试里专门有对抗用例：
20 位串原样保留、12 位串拆不出完整手机号、身份证 `130102199001011234` 的前 11 位
恰好是手机号形状却只按身份证打一次码。身份证的尾部断言还多看一眼：
`(?![\dXx])`——18 位候选后面紧跟 X/x（更像被截断的 19 位串）时不算完整身份证。

**执行顺序：身份证 → 手机号 → 银行卡**。关键在身份证与银行卡的歧义裁决：18 位纯数字
两类都命中（13~19 包含 18），本实现按身份证口径处理——中文客服语境里 18 位数字更
可能是身份证；**两类都会被打码，只是保留位不同**（身份证留前 4 后 2、银行卡留前 4
后 4），不存在漏脱敏。反过来若银行卡先走，末位 X 的身份证会被错拆成"前 17 位银行卡
+ 悬空的 X"。掩码**保头尾**（`138****5678`）：可读性足以让客服人工辨认是哪个客户的
单，但完整号码不再离开工具边界。

两个工程细节：**顺序执行让 `countMasked` 与实际打码数严格一致**——已打码文本带 `*`、
数字串被切断，后续正则不可能对同一位置二次命中；**导出常量刻意不带 `g` 标志**——
带 g 的正则对象有状态（`lastIndex` 会前进），常量复用会踩"第二次 false"的坑，
执行时用 `globalOf()` 克隆出带 g 的副本去 replace。

### 3.2 输入闸：注入扫描（validate.ts）

> 导出入口：`inspectTextInput(text)` 返回 `{ ok, matchedPattern }`；allowlist 解析用 `resolveToolAllowlist` / `isToolAllowed`。

注入话术的对抗面是「**写法**」而不是「意思」：攻击者会用全角字母（ＩＧＮＯＲＥ）、
零宽字符夹带（`ig\u200Bnore`）、leet 数字替换（`ign0re`）绕过字面黑名单。对策分两层：

**规范化先行三步**（`normalizeForInjectionScan`，有损、仅供匹配、不回写原文）：
① 剔除零宽字符（U+200B/U+200C/U+200D/U+FEFF）；② 全角转半角（U+FF01..U+FF5E
平移 -0xFEE0，U+3000 → 空格）；③ 小写化放最后。规范化把"纯写法差异"抹平后，
黑名单只需维护一种写法，对抗面小了一整圈。**leet 替换是漏网之鱼**——o↔0、i↔1
没法无损规范化（会把正常数字文本改坏），由黑名单正则里的**字符类容忍**：
`[i1]gn[o0]r[e3]` 让 `ign0re`、`1gnor3` 这类变体照样命中，匹配用正则、原文不动。

**注入模式清单**（`INJECTION_PATTERNS`，五条，中英双语，对规范化后的文本匹配）：
中文直说（忽略/无视 + 之前/以上/上述/上面 + 指令/提示/设定/规则）→ 英文 ignore 系
（含 leet 字符类 + 有限的 filler 词）→ disregard 变体（同句 60 字符窗口，防跨句误报）
→ 系统提示套取（中文"动词 + 系统提示"、英文 print/reveal your system prompt）。
三类混淆变体的结局（测试逐条断言过）：全角与零宽在规范化后还原成正常写法、命中
黑名单；`ign0re prev1ous instruct1ons` 靠字符类直接命中——写法绕不过，原文也不动。

口径是**宁可漏报也不误伤**：每条都收紧到"动词 + 对象"的组合——"请把这份说明打印
出来"有打印动词但没有系统提示对象，放行；"帮我用手机号查物流"含 PII 但不是注入，
放行（PII 归输出闸管，两个闸职责不重叠）。命中时不回传话术原文（避免注入话术
原样写进工具结果造成二次注入面），只回传模式源码供定位。

**白名单解析**：逗号分隔的工具名，未配置 / 空串 / 全空条目 → `null`（语义 = 不限制，
放行所有工具）；连续逗号、纯空格条目直接丢弃，不产生 `""` 这种永远匹配不上的幽灵项。

### 3.3 门：wrapToolWithGate（gate.ts）

门把两个闸 + 确认 + 原执行编排在替换版 `execute` 里，产出**仍是一个 AgentTool**
（description / inputSchema 原样透传，模型看到的工具面不变，对循环透明）；
无 execute 的 schema-only 工具原样返回。输入闸扫描的是 `JSON.stringify(input ?? {})`：
字符串字段的内容会原样进入序列化文本，扫描面因此覆盖所有字段；无参工具扫 `"{}"` 恒通过。

**拒绝走结构化返回 `{denied, reason}` 而非抛错**——`gate.ts` 头注释给了三条理由：
① 语义错位：拒绝是"策略结果"不是"工具坏了"，模型看到失败会倾向重试或换参数再试，
看到 denied 才会放弃并向用户解释——这正是想要的循环行为；② 结构丢失：引擎的
`runToolLoop` 会把 execute 异常折成 errorOutput（`{error:"工具 X 执行失败：…"}`），
reason 被揉进散文，调用方无法稳定区分"被拦"与"挂了"——**拒绝即数据
（denial-as-data）与 loop 的 error-json 通道是两个通道**；③ 不可移植：闸门按"可用于
任何循环"设计，SDK 版调度 execute 未必有逐调用兜底，拒绝一旦 throw 就可能炸掉整个
运行。结构化拒绝是唯一在所有宿主里都安全的形状：任何宿主循环都活着、模型能看到
原因得体回应用户。

**输出脱敏**（`maskToolOutput`）：JSON 序列化 → `maskPii` → 尽量解析回原结构。
解析失败的兜底是 fail-closed：裸数字字段被脱成 `138****5678` 后不再是合法 JSON，
此时退回**脱敏后的 JSON 字符串**——结构降级好过把未脱敏的原文放出去（测试里
`{"phone":13812345678}` → `'{"phone":138****5678}'` 就是文档化的降级）。序列化本身
失败（循环引用等）时原样返回，注释里标明为理论边界（MCP 工具输出经 JSON-RPC 往返
实际不会出现）。

**confirm 是注入的函数而不是写死的 readline**——依赖倒置：闸门只依赖
`ToolConfirmFn`（`(info) => Promise<boolean>`）这个函数形状，不依赖任何 I/O 设施。
CLI 传 readline y/n 问答（问题写 stderr 保持 stdout 干净），HTTP API 传 SSE 推问 +
审批端点，闸门两边都不认识。回调返回 false **或抛异常**都视为未确认（fail-closed，
闸门不替回调吞错放行）。

### 3.4 CLI 接线：三开关 + stderr 确认问答（apps/cli/src/apps/chat/cli.ts）

引擎三件套是纯函数，真正让它活起来的是 CLI 的装配段（`readGuardSwitches` /
`applyGuardsToMcpTools` / `askToolConfirm`）：

| 环境开关 | 语义 | 生效行为 |
| --- | --- | --- |
| `AGENT_GUARD_PII=1`（或 `true`，与 `AGENT_TRACE` 同款布尔口径） | MCP 工具输出先做 PII 脱敏再回灌模型 | `maskOutput: true` |
| `AGENT_GUARD_ALLOWLIST="t1,t2"` | 只放行名单内的 MCP 工具 | 不在名单 → 结构化拒绝 |
| `AGENT_GUARD_CONFIRM="t3,t4"` | 名单内工具执行前需终端 y 确认 | 只给点名的工具挂 confirm 回调 |

三个开关在启动期读一次快照，全未配置（或全解析为空）→ 整段跳过、零变化；生效时
打印一行中文让使用者知道工具行为被什么改变了。装配点放在 readline 创建之后、
REPL 循环之前——因为确认回调要复用主 REPL 的 readline 接口读答案。

`askToolConfirm` 的实现细节值得细读（Node 22 实测验证过，注释原话）：

- **问题写 stderr、答案走 rl 回显**——stdout 保持干净，与轨迹输出同款纪律；
- **readline 行路由**：`rl.question` 的行路由优先于 `'line'` 事件（kQuestionCallback
  机制），确认答案只进回调、不混进聊天输入流；stdin EOF 时 question 的 Promise
  永不落定——与 `close` 事件竞速，`settled` 标记只认先到的一方，落空按拒绝处理；
- **默认拒绝（fail-closed）**：空输入 / EOF / 非 `y`/`yes` 一律不同意，宁可少执行；
- **已知边界**：管道批量输入的答案行可能已被 REPL 迭代器缓冲（见 3.5 最后一条）。

### 3.5 先说清楚本模块防不住什么

- **正则护栏是概率防线，不是密码学保证**：银行卡正则只看"13~19 位连续数字"的形状，
  不校验 Luhn 校验位——误报（订单号恰好 13 位）与理论上精心构造的漏网都可能发生；
- **只拦"明示型"注入**：编故事绕弯子的语义级改写超出字符串匹配能力，靠提示词分层
  与最小权限工具表兜底（`validate.ts` 头注释原话）；
- **扫描面是文本**：多模态输入（图片/音频里藏指令）不在范围——闸门扫的是入参的
  JSON 序列化，二进制内容它看不见；
- **CLI 确认闸面向交互式终端**：管道批量输入时答案行可能已被 REPL 迭代器缓冲，
  自动化/脚本场景请勿开启 `AGENT_GUARD_CONFIRM`（`cli.ts` 注释已标为已知边界）。

## 四、原理 → 代码对照表（学习自测清单）

| 你应该能回答 | 对应实现 |
| --- | --- |
| 为什么 `ign0re prev1ous` 抓得住？ | `validate.ts`：leet 无法无损规范化，由黑名单字符类 `[i1]gn[o0]r[e3]` 各自容忍 |
| 为什么拒绝不抛错？ | `gate.ts` 头注释三条：语义错位 / 结构丢失 / 不可移植——拒绝即数据是唯一全宿主安全的形状 |
| 为什么身份证先于银行卡？ | 18 位纯数字两类都命中，按身份证口径处理（两者都会被打码，只是保留位不同）；末位 X 的身份证若银行卡先走会被错拆 |
| 为什么 confirm 是注入的函数而不是写死 readline？ | `ToolConfirmFn` 依赖倒置：CLI 的 y/n 问答与 API 的 SSE 审批只是同一个函数形状的两个实现 |
| countMasked 为什么与实际打码数一致？ | `applyPiiMasks` 单一实现 + 顺序推进计数：打码与计数永远同一套口径 |
| 20 位数字串为什么原样保留？ | `(?!\d)` 尾断言 + 银行卡上界 19：嵌在更长数字串里的候选一律不算命中 |
| 导出正则常量为什么不带 g 标志？ | 带 g 的正则有 lastIndex 状态，常量复用会踩"第二次 false"；执行时用 `globalOf()` 克隆 |
| "帮我用手机号查物流"为什么不被拦？ | `validate.ts`：每条模式收紧到"动词 + 对象"，PII 不是注入——输入闸与输出闸职责不重叠 |
| 白名单 null 与空数组的语义差在哪？ | `resolveToolAllowlist` 把未配置/空串折算成 null（不限制）；`isToolAllowed` 对空数组拒绝一切——调用方先过 resolve 不会走到这个分支 |
| maskOutput 之后结构为什么会退化成字符串？ | 裸数字字段脱敏后不再是合法 JSON，`maskToolOutput` 解析失败回退为脱敏后字符串（fail-closed） |
| 前置闸拒绝时为什么不会弹确认？ | 成本排序：白名单/注入是静态闸，任一命中短路返回，confirm 回调根本不被调用（测试断言 confirmCalls=0） |
| confirm 回调抛异常会怎样？ | `gate.ts` try/catch 折成 approved=false：fail-closed，闸门不替回调吞错放行 |
| CLI 护栏为什么只作用于 MCP 工具？ | `cli.ts` 装配段：外部服务器是控制不了的面；本地工具是自己写的代码，全关时逐字节一致 |

**与 API 审批的关系要说准确**：`tool-approval.ts` 与本模块的 confirm 回调是
**同一抽象的两个独立实现**——同样的"工具面包壳"（description/inputSchema 原样
保留、只换 execute）、同样的"确认返回 `Promise<boolean>`"、同样的"拒绝即数据"
（`{ denied: true, reason: "用户拒绝执行该工具" }`，形状与 `ToolGateDenial` 一致）。
但它的头注释写明**刻意不依赖、不 import 本模块**——引擎侧可复用的审批闸门是
另一个工作流，两条线在 Day 5 / Day 6 各自独立落地。对照阅读时重点看：同一个设计
问题（execute 前插一道人工闸、拒绝怎么让模型体面收尾）在 CLI（readline 问答）与
API（SSE 挂起 + UUID 登记簿 + 超时自动拒绝 + sessionId 匹配唤醒）两副基础设施上
的同构解法——这正是 `ToolConfirmFn` 依赖倒置预演的场景。
